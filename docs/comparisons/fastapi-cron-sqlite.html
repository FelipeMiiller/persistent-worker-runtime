SQLite patterns — fastapi-cron vs persistent-worker-runtime

Comparative analysis of the two SQLite designs. Read by AI agents before adopting new patterns; update when either backend changes.

fastapi-cron: 2.0.1 Repo: mE-uMAr/fastapi-crons pwr: 0.2.2-dev pwr ADR: 0020 (revised 2026-09-24) Author: Felipe Miiller

1. Schema

fastapi-cron — 3 tables split by concern

-- Tracks last-run timestamps (one row per job)
CREATE TABLE IF NOT EXISTS job_state (
  name         TEXT PRIMARY KEY,
  last_run     TEXT,
  created_at   TEXT DEFAULT CURRENT_TIMESTAMP,
  updated_at   TEXT DEFAULT CURRENT_TIMESTAMP
);

-- Current execution status (one row per job)
CREATE TABLE IF NOT EXISTS job_status (
  name         TEXT PRIMARY KEY,
  status       TEXT,
  instance_id  TEXT,
  started_at   TEXT,
  updated_at   TEXT DEFAULT CURRENT_TIMESTAMP
);

-- Append-only audit log of every execution
CREATE TABLE IF NOT EXISTS job_execution_log (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  job_name       TEXT,
  instance_id    TEXT,
  status         TEXT,
  started_at     TEXT,
  completed_at   TEXT,
  duration       REAL,
  error_message  TEXT,
  created_at     TEXT DEFAULT CURRENT_TIMESTAMP
);

pwr SqliteTaskQueue — 1 table state column

CREATE TABLE IF NOT EXISTS queue_tasks (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id      TEXT UNIQUE NOT NULL,
  priority     INTEGER NOT NULL DEFAULT 0,
  affinity_key TEXT,
  payload      BLOB NOT NULL,           -- JSON.stringify(task)
  state        TEXT NOT NULL DEFAULT 'pending',
                                       -- pending|processing|done|failed
  attempt      INTEGER NOT NULL DEFAULT 0,
  max_retries  INTEGER NOT NULL DEFAULT 0,
  enqueued_at  INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  claimed_by   TEXT
);

-- Partial index for the hot path
CREATE INDEX IF NOT EXISTS queue_tasks_pending
  ON queue_tasks(state, priority DESC, enqueued_at ASC)
  WHERE state = 'pending';

CREATE INDEX IF NOT EXISTS queue_tasks_affinity_pending
  ON queue_tasks(affinity_key, state, priority DESC, enqueued_at ASC)
  WHERE state = 'pending';
Takeaway: fastapi-cron splits concerns (state vs status vs audit log); pwr uses a single table with a state column. Different model — pwr tracks queue lifecycle (pending → processing → done/failed) per task; fastapi-cron tracks separate axes (last-run timestamp, current status, full audit trail). pwr could borrow the audit-log pattern: keep a separate queue_tasks_history table for completed/failed rows instead of DELETE-ing them in markDone.

2. API surface

fastapi-cron — StateBackend ABC + concrete impls

class StateBackend(ABC):
    async def set_last_run(name, timestamp)
    async def get_last_run(name) -> str | None
    async def get_all_jobs() -> list
    async def set_job_status(name, status, instance_id)
    async def get_job_status(name) -> dict | None
    async def log_job_execution(...)

class SQLiteStateBackend(StateBackend):  # aiosqlite
    async def _get_connection() -> aiosqlite.Connection
    async def _ensure_tables(db)

class RedisStateBackend(StateBackend):  # redis.asyncio
    ...

class SQLAlchemyStateBackend(StateBackend):  # async + sync
    ...

Three backends behind one ABC. Consumers depend on the abstract interface.

pwr — TaskQueue concrete + queueBackend factory

class TaskQueue {
  get size, waitingCount
  enqueue(task) -> Promise
  peek() -> TaskHandle | null
  dequeue(worker) -> TaskHandle | null
  destroy(reason)
}

class SqliteTaskQueue extends // implicit contract {
  // same shape as TaskQueue
  markDone(taskId)
  markFailed(taskId)
  purgePending()
  vacuumCompleted(olderThanMs)
}

// Runtime factory selects backend
createWorkerRuntime({
  queueBackend: 'memory' | 'sqlite',
  sqlite: { path: '/var/lib/pwr/queue.db' },
})

Two concrete classes behind a structural interface (duck-typed). Factory picks one.

Takeaway: fastapi-cron uses Python's ABC for explicit interface contracts; pwr relies on JavaScript duck typing against the same shape as TaskQueue. Both work; ABC gives better IDE/compile-time safety, duck typing avoids ceremony. pwr could borrow: an explicit QueueBackend JSDoc interface + TypeScript declaration for compile-time checking on the consumer side (already partially done in src/index.d.ts).

3. SQLite driver

fastapi-cron — aiosqlite (Python bridge over stdlib sqlite3)

import aiosqlite

async def _get_connection(self):
    if self._db is None:
        self._db = await aiosqlite.connect(self.db_path)
        await self._db.execute("PRAGMA journal_mode=WAL")
    return self._db

# Connection cached, reused across calls.
# aiosqlite runs sync sqlite3 on a shared thread —
# main asyncio loop is NOT blocked (aiosqlite design).

pwr — node:sqlite stdlib (Node ≥ 22.13)

import { DatabaseSync } from 'node:sqlite';

this.#db = new DatabaseSync(options.path);
this.#db.exec('PRAGMA journal_mode = WAL;');
this.#db.exec('PRAGMA synchronous = NORMAL;');
this.#db.exec('PRAGMA busy_timeout = 5000;');

// Sync API on the main thread — fast (~1ms per op on local disk)
// but DOES block the Event Loop. ADR-0020 documents the trade-off
// and the throughput ceiling (~1k ops/sec sustained).
Trade-off: fastapi-cron chose async I/O via a thread pool (aiosqlite spins a thread per connection) so the asyncio loop stays free. pwr chose sync I/O via Node stdlib — fits worker_threads semantics (workers execute; the queue is in-process), and per-op latency is lower because there's no thread-hop. ADR-0020 §Positive Consequences explicitly accepts the Event Loop blocking; benchmark sqlite-queue-throughput.benchmark.js quantifies the cost.

4. Connection lifecycle

fastapi-cron — lazy connection + idempotent schema

async def _ensure_tables(self, db):
    if self._tables_created:
        return
    await db.execute("""CREATE TABLE IF NOT EXISTS ...""")
    await db.commit()
    self._tables_created = True

async def close(self):
    if self._db is not None:
        await self._db.close()
        self._db = None
        self._tables_created = False

pwr — eager in constructor + statement cache

constructor(options) {
  this.#db = new DatabaseSync(options.path);
  this.#db.exec('PRAGMA journal_mode = WAL;');
  this.#db.exec('PRAGMA synchronous = NORMAL;');
  this.#db.exec('PRAGMA busy_timeout = 5000;');
  this.#db.exec(SCHEMA);
  this.#recoverPending();   // scan state='pending' rows on startup
}

#stmt(key, sql) {
  let stmt = this.#statementCache.get(key);
  if (!stmt) {
    stmt = this.#db.prepare(sql);
    this.#statementCache.set(key, stmt);
  }
  return stmt;
}

destroy(reason) {
  // rejects waiters, closes connection
  this.#db.close();
}
Takeaway: fastapi-cron is lazy (open DB on first call). pwr is eager (open + schema + recovery in constructor). pwr adds a statement cache (prepared statements reused across calls) — fastapi-cron does NOT cache, every call recompiles. pwr could borrow: a close() method separate from destroy() for clean shutdown vs crash simulation. (Already addressed — pwr has destroy() leaving pending rows for rolling-deploy recovery + purgePending() for explicit cleanup.)

5. Upsert semantics

fastapi-cron — INSERT OR REPLACE for SQLite

await db.execute(
    """INSERT OR REPLACE INTO job_state (name, last_run, updated_at)
       VALUES (?, ?, ?)""",
    (job_name, timestamp.isoformat(), now_iso),
)
await db.commit()

# For terminal status, the library uses INSERT + ON CONFLICT
# to preserve started_at across instance races (the SELECT inside
# the COALESCE protects against losing the original start time).

pwr — ON CONFLICT DO UPDATE

INSERT INTO queue_tasks (task_id, priority, ..., state, ...)
VALUES (?, ?, ..., 'pending', ...)
ON CONFLICT(task_id) DO UPDATE SET
  priority = excluded.priority,
  affinity_key = excluded.affinity_key,
  payload = excluded.payload,
  state = 'pending',
  attempt = excluded.attempt,
  max_retries = excluded.max_retries,
  updated_at = excluded.updated_at

// Equivalent semantic but EXPLICIT — fields not in SET keep
// their previous value. INSERT OR REPLACE deletes+re-inserts
// (any field not listed gets the default).
Takeaway: INSERT OR REPLACE is simpler but DELETEs the row first — any column not in the VALUES list reverts to its default (e.g. created_at = CURRENT_TIMESTAMP would reset on every update). ON CONFLICT DO UPDATE is more verbose but keeps untouched columns intact. pwr chose the more explicit form on purpose (preserves enqueued_at across retries / re-enqueues).

6. Concurrency model

fastapi-cron — asyncio.Lock per backend

def __init__(self):
    self._lock = asyncio.Lock()
    self._db = None
    self._tables_created = False

async def set_last_run(self, name, ts):
    async with self._lock:    # serialize writes
        db = await self._get_connection()
        await self._ensure_tables(db)
        await db.execute("INSERT OR REPLACE ...", (...))
        await db.commit()

# Reads are NOT lock-guarded (parallel-safe with WAL).
# Writes go through _lock to serialize across coroutines.

pwr — BEGIN IMMEDIATE transaction

this.#db.exec('BEGIN IMMEDIATE');   // db-level write lock
try {
  this.#stmt('dequeue-affinity', "SELECT ...").get(targetAffinity);
  // ...
  this.#stmt('claim-processing', "UPDATE ...").run(now, claimedId);
  this.#db.exec('COMMIT');
} catch (err) {
  this.#db.exec('ROLLBACK');
  throw err;
}

// BEGIN IMMEDIATE acquires SQLite's reserved lock for the
// duration of the txn — atomic state transition (claim a row
// + mark processing in one indivisible step). Faster than
// asyncio.Lock for high-throughput because no JS hops.
Trade-off: fastapi-cron's asyncio.Lock serializes writes at the JS layer (cheap); pwr's BEGIN IMMEDIATE serializes at the SQLite layer (more correct under multi-instance writes, because SQLite-level locks compose with file-locks across processes). For pwr's threat model (multi-instance writers via NFS), BEGIN IMMEDIATE is the right choice. For fastapi-cron's threat model (one Python process, asyncio concurrency), asyncio.Lock is sufficient.

Async or sync API async (aiosqlite) sync (node:sqlite)

Retention / GC none in SQLite path; relies on caller vacuumCompleted(olderThanMs)

Patterns pwr could adopt:
  • PRAGMA synchronous = FULL opt-in for users who want stronger durability than NORMAL (currently hardcoded).
  • An audit_log table for completed/failed tasks (fastapi-cron pattern).
  • An extras opt-in for advanced features (retention, snapshot export) — fastapi-cron uses pip install fastapi-crons[sqlalchemy].
Patterns fastapi-cron could adopt:
  • PRAGMA busy_timeout to avoid SQLITE_BUSY under contention.
  • PRAGMA synchronous = NORMAL for faster commits (already documented as a tuning option).
  • Prepared statement caching (recompile cost is non-trivial at high QPS).

8. Patterns worth borrowing — quick reference

  • audit_log_table Add queue_tasks_history for completed/failed rows instead of DELETE. Operations teams get post-mortem visibility without changing the hot path.
  • multi_backend_ABC Add an explicit QueueBackend interface (JSDoc + d.ts) so the runtime's contract is visible to TypeScript consumers. Already partially done; tighten the SqliteTaskQueue class to formally implement it.
  • on_conflict_started_at pwr's attempt column could grow a started_at mirror like fastapi-cron's status table — preserves the original dispatch start across retries.
  • migration_helper Both libraries are stuck on CREATE TABLE IF NOT EXISTS. fastapi-cron exposes cron_metadata for Alembic; pwr should at least document a manual migration path when adding columns to queue_tasks.
  • distributed_lock fastapi-cron ships a DistributedLockManager for multi-instance dispatch coordination. pwr's SQLite BEGIN IMMEDIATE handles the queue atomicity; for multi-instance worker selection (which task to claim next), pwr would need a separate lock layer.

9. Closing notes

Both designs are correct for their respective runtimes. fastapi-cron optimizes for asyncio concurrency with low write volume; pwr optimizes for sync I/O on a single Node process with potentially high write volume. The schema choices (3 tables vs 1) reflect different concerns: fastapi-cron models a cron scheduler (timing + status + history); pwr models a task queue (lifecycle + payload + priority).
